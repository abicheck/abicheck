# `set-up-abi-compatibility-ci` A/B evaluation — 2026-09-30

**Setup.** Headless Claude Code (`claude -p`, `claude-sonnet-5-5`), 5
scenarios × 2 arms × 3 repetitions = 30 runs per pass. The arms are identical
(prompt, tools including web access, turn budget, model) except that the
`skill` arm has the skill installed in the workspace's `.claude/skills/`.
Graded by `grader.py` (deterministic, no model).

not hinge on any one debatable check.

**What the baseline did well** (worth stating, since several baseline
workflows were good engineering): no run used `pull_request_target`, none
granted `contents: write` to a PR job, none self-compared, and several chose
a sound "rebuild the latest release tag and compare" strategy, which the
grader accepts as a valid release baseline.

## How the evaluation itself was corrected along the way

Each of these was found by reading transcripts, not by the numbers:

1. **Smoke run (1 run, skill v1).** The agent hand-installed
   `apt-get install castxml` for the release dump. Skill fixed (use the
   Action's `mode: dump`; distribution CastXML is below the supported range);
   `toolchain_via_action` check added.
2. **Run 1 (30 runs, skill v2).** Skill 15/15 vs baseline 0/15, but two
   problems with the *measurement*:
   - The grader recognised only Action steps. Several baseline runs called
     the CLI in `run:` steps with a sound tag-rebuild strategy and were scored
     as "no check at all". The grader now maps CLI calls onto the same checks
     and accepts a tag rebuild as a release baseline; run 1's baseline score
     rose from 0.55 to 0.67 on regrade (success stayed 0/15).
   - **Leak.** A skill-arm agent ran `find / -name action.yml`, found this
     abicheck checkout, and read `action.yml` directly — impossible for a real
     user. Run 2 therefore runs every agent in a private mount namespace with
     this checkout, all other runs' outputs and the parent session's
     transcripts hidden behind empty tmpfs mounts, and abicheck installed from
     a wheel into a separate venv (`--abicheck-venv`).
   - Also found in run 1: 4 of 14 SHA pins used the annotated tag *object*
     SHA (`2ff668d…`, the plain `refs/tags/v0.6.0` line) instead of its commit
     (`a1f78b6…`, the `^{}` line); such a `uses:` does not resolve. Skill
     fixed (explicit `^{}` rule); `pins_are_commits` check added. Run 2: 15/15.
3. **Run 2 (30 runs, skill v3, isolated).** The numbers above.

`2026-09-30-run1.json` and `2026-09-30-run2.json` hold the per-run grades
(run 1 regraded with the CLI-aware grader, before `pins_are_commits` existed).

## Limits — read before citing

- **Static grading.** No workflow ran on GitHub. A workflow passing every
  check can still fail at runtime for a reason no check models.
- **Not held out.** The scenarios and checks were written together with the
  skill, and the skill was revised twice against this corpus.
- **One agent, one model.** Not cross-agent evidence.
- **The checks encode the skill's own opinions** in places (`lang` always set
  for C, debug info, `permissions:` everywhere). The sensitivity analysis
  above bounds how much that matters to the headline.
- **Baseline prompt realism.** One scenario does not name abicheck; the
  baseline reasonably chose `abidiff` there and is graded as not integrating
  abicheck. That scenario measures triggering and tool choice as much as
  configuration quality.

## Found in passing (product, not skill)

abicheck's own "castxml not found" error recommends `apt install castxml`,
which on current Ubuntu images commonly installs a CastXML below abicheck's
supported range (`castxml_policy.py`). A user following the error message
lands on a second, less obvious failure.
