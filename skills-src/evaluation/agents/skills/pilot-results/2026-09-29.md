# G37 second pilot: `check-abi-compatibility`, 2026-09-29

This is the second real A/B run of `skills-src/evaluation/agents/skills/`, and the first with
the harness defects below fixed. It covers all 14 `status: ready` scenarios
and uses one model, `claude-sonnet-5-5`, recorded as the resolved model on
every run. It was run headless through `runners/claude_code.py` with
`--max-turns 40`. It is still a pilot: two or three repetitions per cell, one
model, one agent, one host. It does not replace the cross-agent validation
that `skills-src/CLAUDE.md` still lists as open.

## Result

|                                   | skill (v2) | baseline  |
|-----------------------------------|-----------:|----------:|
| runs graded                       | 30         | 28        |
| correct verdict                   | 30 (100%)  | 22 (79%)  |
| ran a real comparison (dim 1/3)   | 28 (93%)   | 15 (54%)  |
| claim well-formed                 | 30 (100%)  | 27 (96%)  |
| zero-tolerance failures (dim 2/6) | 2 (7%)     | 19 (68%)  |
| mean cost / turns / wall time     | $0.156 / 7.4 / 25 s | $0.108 / 5.7 / 23 s |

**Where the skill changes the outcome.** Per scenario, correct verdicts for
skill vs baseline:

| Scenario | Skill | Baseline |
|---|---|---|
| `constant-value-changed` | 2/2 | 0/2 |
| `evidence-too-shallow` | 3/3 | 0/2 |
| `contract-coverage-incomplete` | 3/3 | 1/2 |
| `changed-signature` | 2/2 | 1/2 |

In every other scenario both arms were right.

The larger effect is **how** the answer is reached, more than whether the
verdict is right. In 13 of the 28 baseline runs the agent never ran a
comparison. It answered from reading the diff, sometimes correctly, and still
stated a compatibility conclusion, which is what dimension 6 counts as a
zero-tolerance failure. Two examples:

- The `constant-value-changed` baseline reported a source-compatible constant
  change as compatible.
- The `evidence-too-shallow` baseline either trusted a stripped-binary
  `NO_CHANGE` for a struct-layout question or gave up.

The two remaining skill failures are both `consumer-actually-affected`, on
dimension 6. The agent correctly built the consumer from
`consumer/analytics-daemon.c` as `./daemon` and scoped to it with
`--used-by daemon`. The grader matches the `--used-by` operand's name against
the scenario's declared label `analytics-daemon` and rejects the mismatch.
That is a grader strictness limitation, not a skill error: the scoped verdict
was right. It hits both arms equally, since the same check failed in the v1
baseline runs.

## How v2 differs from v1, and the caveat that comes with it

The v1 skill run (same batch as the baseline above) scored 24/28 correct. It
missed:

- **`evidence-too-shallow`, 0/2.** The skill reported `verdict: null`
  ("not comparable") when the tool *had* compared and produced a verdict that
  was too shallow for the question.
- **`contract-coverage-incomplete`, 0/2.** For "anything we actually export",
  the skill never selected `--contract exports`, so it never saw that the
  export table's coverage was incomplete.

Two general guidance changes fixed these:

1. **Step 1:** map the user's wording to a `--contract` domain.
2. **Step 5:** "too shallow is not the same as not comparable". Keep the
   observed verdict and mark the question `NOT_VERIFIED`.

The skill arm was then re-run on all 14 scenarios to check for regressions.
The baseline arm does not depend on the skill, so its v1 runs stand.

**Caveat:** v2 was revised after seeing v1's failures on this same corpus, so
its 30/30 is not a held-out result. The changes are stated as general rules
rather than fixture-specific ones. Neither rule names a fixture, and each
covers a whole class of question ("which surface does the promise cover?" and
"what does a shallow verdict still say?"). But proving that they generalize
needs scenarios the revision never saw. The next corpus additions should be
held-out variants of both classes.

## Harness defects found and fixed while producing this run

Each of these would have produced a plausible-looking but meaningless table:

1. **The recording shim was bypassed.** Launched from inside a Claude Code
   session, the child `claude` inherited the parent's session id and
   re-sourced its SessionStart environment. That put the real `abicheck`
   ahead of the shim on `PATH`. Every call ran unrecorded and was graded as
   "never compared" in both arms.
   - Fix: parent-session variables are dropped from the child environment.
   - Guard: a run that invokes `abicheck` with an empty calls log is now
     rejected (`_shadowed_the_recorder`).
2. **The answer and the arm were in the agent's working directory.** Claude
   Code puts the cwd in the system prompt, and it was
   `<out>/<scenario>/<arm>/<rep>/workspace`. That exposed the scenario name,
   e.g. `compatible-addition` or `consumer-unaffected-despite-break`, and
   whether this was the `skill` or `baseline` arm. The 2026-08-20 pilot ran
   under the same layout.
   - Fix: each run now lives in a random-named directory under `<out>/.runs/`.
     The readable path is a symlink that graders and resume use.
3. **An `--out` under a path containing `abicheck` handed the baseline the
   tool's name.** Its first command was `which abicheck`. `--out` paths that
   name the tool or a verdict word are now refused.
4. **`tests/test_gen_harbor_tasks.py` raced under `pytest -n`.** Those tests
   now work on a private copy of the task tree.

## Reproducing

Run from a path containing neither `abicheck` nor a verdict word:

```bash
python scripts/gen_agent_skills.py
python skills-src/evaluation/agents/skills/runners/claude_code.py --out /tmp/se/a --repetitions 2 \
    --scenarios changed-signature,compatible-addition     # repeat per subset, in parallel
python skills-src/evaluation/agents/skills/run_skill_eval.py --runs /tmp/se/a --runs /tmp/se/b ...
```

`run_skill_eval.py` accepts `--runs` more than once and grades the union. The
one-model check spans every root.
