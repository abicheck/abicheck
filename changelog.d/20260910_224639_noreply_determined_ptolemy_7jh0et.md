### Changed

- **GitHub Action: `mode: scan` now routes to `compare`/`compare --no-baseline` unconditionally** — closing the last gap ADR-068's second 2026-09-09 amendment left open. An audit-only `mode: scan` step (no `against`/`abi-baseline`) no longer falls back to the legacy `scan` CLI; it is translated to `compare --no-baseline` like every other request shape already was. To preserve `mode: scan`'s documented default-gating behavior, the Action injects `severity-preset: default` on the translated invocation whenever the step states no preset of its own (`policy/audit_gate_exit.py`'s opt-in audit-gate exit axis, exit code `3`) — an explicit `severity-preset` (including `info-only`) is always honored instead. The Action's `verdict` output gains a new `AUDIT_GATE` value for this axis, alongside `COVERAGE_INCOMPLETE`/`SEVERITY_ERROR`, and it fails the step unconditionally like the other orthogonal axes.
- **GitHub Action: `budget` is forwarded again for `mode: scan` with a baseline**, and `since`/`changed-path`/`budget` on an audit-only `mode: scan` step (no baseline) now fail fast with a clear, specific `::error::` instead of either a bare `compare` usage error or (for `budget`) silently doing nothing — `compare --no-baseline` does not implement revision-range evidence scoping or the wall-clock guard yet (ADR-068 D2); set `against:` to use any of the three. `require-complete-analysis` is once again a documented no-op on an audit-only step (it had gained real, undocumented effect through the `compare --no-baseline` translation).
- **Sticky PR comment: `compare --no-baseline`'s audit-report JSON (`audit_report_schema_version`) is now a recognized report shape** (`abicheck.pr_comment.build_model`) — a gating audit-only `mode: scan` finding no longer silently renders as "No ABI changes" and, under the default `pr-comment-on: changes`, is no longer silently dropped from the sticky comment (or a previous one deleted). The comment's headline for this shape no longer reuses two-sided wording ("ABI BREAKING", "Source API changed; binary ABI unchanged") that falsely implies a before/after comparison — it says plainly whether `policy/audit_gate_exit.py`'s own axis actually blocked the step (read from the report's own `exit_axes.audit_gate`, not re-derived from bucket membership). `gcc-options` on `mode: scan` is documented as sharing dump/single-pair-compare's own synthesized `compile:` block, including its one-atom-per-entry, whitespace-free contract — a real, accepted narrowing from `scan`'s now-removed `--compiler-option` CLI flag, which forwarded a whitespace-containing flag verbatim.
- **Sticky PR comment: a fully-suppressed no-baseline audit now still posts**, and the headline for a no-baseline audit now checks the report's own overall `exit_code` (every orthogonal exit axis max-folded in — including `evidence_contract`'s exit `7`, which can block with no itemizable finding at all) *before* falling back to bucket membership, so a run blocked on an axis with an empty finding bucket no longer renders a green "no baseline to compare" headline. The audit report's `policy` field is no longer invented at the comment layer — it is threaded through from `DiffResult.policy` → `NoBaselineDocument` → the JSON report (`audit_report_schema_version` bumped `1.1` → `1.2`, purely additive).
- **GitHub Action: `mode: scan` preflight no longer rejects an audit-only-looking request that actually has a baseline via `abi-baseline`** — `action/validate-inputs.sh`'s since/changed-path/budget rejection (added above) ran before `run.sh`'s later `abi-baseline` → `against` resolution, so a step using `abi-baseline:` instead of `against:` was misclassified as audit-only and rejected even though it has a real two-sided comparison.
- **GitHub Action: exit-0 audit-only `mode: scan` no longer reports the generic `COMPATIBLE` verdict**, which falsely implied a two-sided "no binary ABI break detected" comparison ran. Two new verdicts distinguish the two exit-0 shapes: `AUDIT_CLEAN` (no candidate-side finding at all) and `AUDIT_RISK` (a real finding present, but RISK-classified and so never gated by `policy/audit_gate_exit.py`) — a fully-suppressed audit (every finding matched by a `--suppress` rule) now also reports `AUDIT_RISK`, not `AUDIT_CLEAN`, since a suppressed finding is a disposition, not an absence.
- **Docs: `format: text` on `mode: scan` is now documented as what it actually is** — `scan` has no CLI of its own left (ADR-068), so `text` is rendered through `compare`'s own markdown renderer for both a baseline scan and an audit-only one, not a separate plain-text report format. `action.yml`'s `verdict` output description no longer claims `AUDIT_GATE`/`AUDIT_CLEAN`/`AUDIT_RISK` are reachable through a native `mode: compare` request with `--no-baseline` in `extra-args` — this Action's own compare branch always supplies both `old-library` and `new-library` as positional operands, and `--no-baseline` takes exactly one, so that combination always fails with a CLI usage error instead; the three verdicts are reachable only through `mode: scan`'s own audit-only translation.
- **Sticky PR comment: a no-baseline audit blocked solely on an axis with no itemizable finding** (e.g. `evidence_contract`'s exit `7` — a pinned `--depth` whose required evidence never materialized) **now still posts under `--on=changes`** instead of producing no comment (or deleting a previous sticky one) for a run its own headline already renders as 🛑 blocking — `should_post()` now also checks `model.no_baseline_audit_blocking`, the same signal the headline itself reads.
- **GitHub Action: combining `extra-args: --write FORMAT=...` (a non-json secondary format) with a `compare`/`scan` PR-comment run no longer silently drops the internal JSON report `run.sh` needs to render the sticky comment/recognize a no-baseline audit shape.** `--write` is documented and live-verified as *repeatable* for a single-pair or audit-only operand — the Action's own suppression logic previously assumed (incorrectly) that a second `--write` would silently lose to the user's own, so it unconditionally skipped its internal `--write json=...` injection whenever `extra-args` carried *any* `--write` at all. It now only skips injection when the user's own `--write` is already `json=...` (redundant) or the operand is a directory/package (release) comparison, where the CLI genuinely supports only one `--write`. `severity-preset`'s own input description also no longer claims it "only applies to compare mode" — it has applied to `scan` (both the baseline and audit-only shapes, including as the documented opt-out from this Action's own injected default audit gating) since `scan` moved onto `compare`.
- **GitHub Action: a baseline `mode: scan` step that overruns its `budget` now correctly reports `BUDGET_OVERFLOW` (exit `5`) again** instead of the generic `ERROR` — the shared `compare`/`mode: scan` exit-code dispatch this Action routes both through had no `5)` case arm (exit 5 previously fell into the catch-all `ERROR` case), skipping the budget-specific job-summary/comment handling `mode: scan` has always used for this outcome. `action.yml`'s `exit-code` output description also now lists scan's exit `3` (`AUDIT_GATE`), which it had omitted.
