### Security

- **The composite Action's assurance-overlay generation step no longer runs Python directly against the untrusted checkout.** `actions/check-target/action.yml`'s "Generate assurance-overlay config" step (which runs whenever a project's `.abicheck.yml` declares `checks[].analysis.assurance: complete`) now launches its inline Python helper from a fresh, private temporary directory with `PYTHONPATH` cleared — the same `$_PY_SAFE_DIR`/cleared-`PYTHONPATH` mitigation `action/run.sh` already uses for its own inline Python invocations. Without this, a pull request that planted a top-level `sitecustomize.py` and declared that config value could get arbitrary code execution in this Action's context, since Python's `site` processing auto-imports a discoverable `sitecustomize.py` during interpreter startup, before the step's own script body ever runs.

### Fixed

- **The assurance-overlay step no longer silently disables a project's auto-discovered `.abicheck.yml` settings.** When `analysis-assurance-complete: true` was given with no explicit `build-config`, the generated overlay previously started from an empty document and was then passed as an explicit `--config` to the nested root Action — which disables normal `.abicheck.yml` auto-discovery, silently dropping every other project setting (scope, severity, policy overrides, compile context, ...). The step now discovers the project's real `.abicheck.yml` (the same way `discover_project_config()` does) and merges the `assurance: {require_complete: true}` overlay into that document instead.
- **`action/run.sh`'s `_assurance_gated()` now also reads the no-baseline/`scan`-mode report shape.** A `mode: scan`/`--no-baseline` audit-only run publishes its analysis-assurance exit contribution under `exit_axes.analysis_assurance` rather than the top-level `analysis_assurance_exit_contribution` key the two-sided `compare` shape (or `diff.analysis_assurance_exit_contribution` for `scan --against`) uses. Previously this third shape was not consulted, so an audit-only run with `assurance.require_complete: true` was reported as a plain error rather than `ANALYSIS_INCOMPLETE`, even though the CLI itself correctly exited 1.
- **The persisted contract-context receipt's `gate.require_complete_analysis` provenance entry now identifies the real config document that supplied it.** `contract_context.with_resolved_gate` now accepts the caller's already-resolved project-config path/digest and threads them into the entry (`path`, `sha256`, and a `selected_by` hop), the same identity every other project-config-sourced `field_provenance` entry in the receipt already carries. Previously the entry named only the `PROJECT_CONFIG` layer, so a project whose `.abicheck.yml` set only `assurance.require_complete` (no other override) left the receipt unable to identify or replay which exact document enabled the gate.
