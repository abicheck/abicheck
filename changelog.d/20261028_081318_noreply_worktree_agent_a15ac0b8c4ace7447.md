### Fixed

- **The one-line summary's total counts the same findings as the JSON report** — `compare -o oneline=...` (and `--stat`) left standing cross-source hygiene findings out of its total while the JSON `summary.total_changes` counted them, so a run with one persistent `exported_not_public` printed `2 breaking, 2 compatible (4 total)` beside a JSON total of 5. Those findings are now a `N header/binary consistency` clause within the breakdown, so the parts add up to the same total the JSON reports. The `; hygiene: ...` suffix still names their states. Text output only; the JSON report is unchanged.
- **A release's one-line total counts a finding that was not evaluated** — `compare -o oneline=...` on a directory or package summed the outcome buckets for its total, and a finding contract evaluation left `NOT_EVALUATED` is in no bucket. Such a finding was dropped from the total (`BREAKING: no changes (0 total)` beside a JSON `total_changes` of 1), or, when it carried a standing hygiene stamp, printed as a negative `-1 not evaluated`. The total is now the release inventory's observed changes plus its hygiene findings, which is the population the JSON reports; a `N not evaluated` clause states the unscored findings. A member entry without an inventory block (a release-support-promise entry) is folded into the same count rather than dropped. Text output only.
- **A consumer-scoped JSON summary counts a policy-demoted break as a quality issue** — with `--used-by` or `--required-symbol`, the summary buckets were recounted from the raw kind of each change, so a removal a `reclassify:` rule demoted to COMPATIBLE was counted as an addition while the full summary counted it as a quality issue. Quality issues are now read from the change's `recommended_action`, which follows the same effective classification the full summary uses.
