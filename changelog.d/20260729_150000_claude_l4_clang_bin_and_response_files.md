### Fixed

- **L4 source-ABI replay and S2 preprocessor pre-scan now honor `--gcc-path`/`--gcc-prefix` for `dump --sources`/`--build-info` too, not just `scan`'s S2 stage.** `cli_buildsource.embed_build_source()`'s `clang_bin` (used by inline L4 replay) previously always defaulted to a bare `clang`, ignoring the dump's own resolved compiler override — a dump built with a non-default toolchain (e.g. `--gcc-path icpx`) silently replayed L4 through the wrong compiler and failed every translation unit. Both `dump`'s and `scan`'s `embed_build_source()` calls now resolve `clang_bin` the same way the S2 pre-scan already did, via a new shared `dumper_clang.resolve_source_frontend_clang_bin()`.
- **`compile_commands.json` entries using a GNU `@response-file` argument (e.g. `@build/inc_folders.txt` instead of literal `-I` flags — common for make-based build systems with long include-dir lists) are now expanded inline**, so their `-I`/`-D` flags reach both the L2 header-flag parser and the L3 `CompileUnit` build evidence instead of silently vanishing as one opaque `@file` token (previously causing `file not found` on every translation unit). `buildsource.include_graph.depfile_args_from_argv()`'s own `@file` handling for the `clang -MM` depfile replay is expanded the same way when a compile unit's working directory is available, instead of being dropped — expansion happens before the existing unsafe-flag filtering, so a flag smuggled inside a response file is still denied. Both expansion sites are jailed to a trusted root (the compilation database's own directory, or the compile unit's working directory) the same way the existing `adapters/make.py` response-file expansion already is, so an untrusted `compile_commands.json`/build-evidence pack (e.g. scanned from a PR checkout) can't use an absolute or `../`-traversal `@file` token to read arbitrary filesystem content into the parsed argv.
- **Response-file quoting is now selected by the compiler driver actually invoked, not the host OS.** Both `@file` expansion sites above previously dispatched purely on `os.name` (Windows → MSVC/`CommandLineToArgvW` quoting, everything else → POSIX shell quoting), so a MinGW GCC or GNU-mode `clang++` entry running on Windows had its response-file quoting corrupted (a quoted path or backslash-escaped space split into multiple tokens), and conversely a `clang-cl`/`dpcpp-cl`/`cl.exe` entry on a non-Windows host would have used the wrong quoting too. A new `build_context._is_cl_style_driver()` inspects the compile entry's own driver token (recognizing versioned spellings like `clang-cl-20`, and unwrapping a `ccache`/`sccache`/… launcher prefix first) and both expansion sites now thread that decision through explicitly.
- **`load_compile_db()` no longer re-reads/re-tokenizes the same `@response-file` for every entry that references it, and now also bounds aggregate expansion work across the whole database.** Each `CompileEntry.from_dict()` call previously started with a fresh response-file read/output budget, so a database with many entries pointing at one file paid its full read+tokenize+expansion cost again per entry — for an untrusted `compile_commands.json` (e.g. scanned from a PR checkout) with thousands of such entries, this could amplify a few MB of JSON into a much larger amount of I/O, parsing, and list-allocation work. A shared per-database `_ResponseFileCache` now memoizes a response file's own tokenization by resolved path, and a shared database-wide output-token budget additionally caps the aggregate expansion size across every entry, independent of entry count.
- **The L4 source-ABI per-TU cache key (`--source-abi-cache-dir`) now folds in the resolved `--gcc-path`/`--gcc-prefix` compiler override.** Previously the cache key was insensitive to which compiler was actually selected, so a cache warmed under the default `clang` would be silently treated as a hit for a later run honoring a different `--gcc-path` override, reusing stale source-ABI facts produced by the wrong compiler. `ClangSourceExtractor` now exposes a `cache_identity_extra()` hook (mirroring the existing `effective_public_header_roots_for_cache()` pattern) that folds `clang_bin`/`compiler_binary` into the cache key, and `CLANG_EXTRACTOR_VERSION` was bumped to invalidate any cache populated before this change. `compute_tu_cache_key()`'s `replay:` component (the argv-only forced-include/search-path flags) also now takes the same override, since an override that switches a GNU-argv compile unit into CL mode changes which flags are recognized (`/FI`/`/I` vs `-include`/`-iquote`) — without it, two compile units differing only in their `/FI` forced-include target could collide onto the same cache key under a CL-mode override.
- **`load_compile_db()`'s response-file cache no longer retains the full token list for a file too large for any entry to ever use.** A response file whose own token count exceeds the fixed per-entry output-token cap can never fit any entry's budget (no entry starts with a larger one), so caching its full tokens list anyway wasted memory for no benefit; the cache now records a lightweight rejection instead once a miss's tokenization turns out oversized, so many distinct oversized files in one untrusted database no longer each retain a large, permanently unusable list. A separate, dedicated `_cache_token_budget` now also bounds *aggregate* cached memory across the whole database load — a distinct file under that fixed per-entry cap but over one particular entry's own already-partially-spent budget was previously still retained in full for possible reuse, so many such distinct, never-actually-used files could accumulate unbounded cached memory without ever charging the existing database-wide output budget (which only charges tokens actually used in some entry's output).
- **`load_compile_db()` now resolves a symlinked `compile_commands.json` before deriving the response-file trust jail from it.** A build directory's `compile_commands.json` is commonly symlinked into the source tree; using the symlink's own parent directory as the trusted root treated every `@file` beside the real (target) database as out-of-tree and left it unexpanded even though the database itself was read successfully through the symlink.
- **`buildsource.include_graph.depfile_args_from_argv()`'s response-file expansion no longer self-jails to `directory` alone.** `directory` (typically `CompileUnit.directory`) can be attacker-controlled free-form content for a compile unit sourced from an untrusted build pack (e.g. a third-party `abicheck_inputs/` drop) — jailing an expansion to a root the same untrusted input also chose was not a real jail (an attacker could set `directory` to a sensitive path and reference a secrets file relative to it, leaking its content into scan diagnostics/artifacts). The function now takes a separate, keyword-only `trusted_root` and only expands when one is independently supplied; none of the current call sites have one yet, so they now correctly fall back to the existing safe "drop the token" behavior instead of expanding against a self-chosen root.
- **L4 source-ABI replay now preserves SYCL language mode (`-fsycl`/`-fsycl-*`) when a resolved `--gcc-path` override actually invokes `icpx`/`dpcpp`.** L4 previously always replayed through a bare `clang` (fixed above to honor the real override), which meant a SYCL translation unit was never actually reparsed by a SYCL-aware compiler in the first place; now that it can be, `-fsycl`/`-fsycl-*` needed to be captured by `adapters.base.ABI_RELEVANT_FLAG_PREFIXES` (like `-std=`/`-fvisibility`) to reach the reconstructed replay command via the existing `abi_relevant_flags` carry-through — without it, a SYCL TU would replay as plain C++, silently missing built-in SYCL state. Reconstructing the real build's own host/device multi-pass invocation (e.g. forcing `-fsycl-host-only`, or parsing legacy `dpcpp`'s multi-document AST output) is a separate, deeper piece of work and out of scope here — see the "Known gaps" section in `AGENTS.md`.
