### Fixed

- **L4 source-ABI replay and S2 preprocessor pre-scan now honor `--gcc-path`/`--gcc-prefix` for `dump --sources`/`--build-info` too, not just `scan`'s S2 stage.** `cli_buildsource.embed_build_source()`'s `clang_bin` (used by inline L4 replay) previously always defaulted to a bare `clang`, ignoring the dump's own resolved compiler override — a dump built with a non-default toolchain (e.g. `--gcc-path icpx`) silently replayed L4 through the wrong compiler and failed every translation unit. Both `dump`'s and `scan`'s `embed_build_source()` calls now resolve `clang_bin` the same way the S2 pre-scan already did, via a new shared `dumper_clang.resolve_source_frontend_clang_bin()`.
- **`compile_commands.json` entries using a GNU `@response-file` argument (e.g. `@build/inc_folders.txt` instead of literal `-I` flags — common for make-based build systems with long include-dir lists) are now expanded inline**, so their `-I`/`-D` flags reach both the L2 header-flag parser and the L3 `CompileUnit` build evidence instead of silently vanishing as one opaque `@file` token (previously causing `file not found` on every translation unit). `buildsource.include_graph.depfile_args_from_argv()`'s own `@file` handling for the `clang -MM` depfile replay is expanded the same way when a compile unit's working directory is available, instead of being dropped — expansion happens before the existing unsafe-flag filtering, so a flag smuggled inside a response file is still denied. Both expansion sites are jailed to a trusted root (the compilation database's own directory, or the compile unit's working directory) the same way the existing `adapters/make.py` response-file expansion already is, so an untrusted `compile_commands.json`/build-evidence pack (e.g. scanned from a PR checkout) can't use an absolute or `../`-traversal `@file` token to read arbitrary filesystem content into the parsed argv.
