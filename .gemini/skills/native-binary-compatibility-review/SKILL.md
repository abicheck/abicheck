# Reviewing a native change for compatibility

You are reviewing a change that has **already been made** to a compiled
library, and answering: does it break consumers, and if so, why and what
should be done. Diagnosis, not design (that is `native-api-evolution`) and
not a release decision (that is `native-release-compatibility`).

Read [safety invariants](references/shared/safety-invariants.md)
before reporting anything. The rule that governs this whole workflow: a
category you could not check is unverified, never clean.

## Preflight — abicheck availability and version range

Run `abicheck --version` before anything else and check the reported version
against this skill's declared version range (`metadata.abicheck-version-range`
in this file's own frontmatter). Outside that range — **below the minimum or
at/above the maximum** — stop and say so rather than proceeding on an
unvalidated version: below the minimum the surface this workflow uses may not

If abicheck is not installed, say so and how to install it. Do not install it
yourself ([safety invariants](references/shared/safety-invariants.md) item 8).

## Step 0 — Establish what is being asked

Which compatibility contract does the user mean — binary (installed
consumers, no rebuild), source API (their code still compiles), or runtime
(the binary still loads in a new environment)? The answers diverge. See
[compatibility contracts](references/shared/compatibility-contracts.md).
When the user has not said and the answers would differ, answer both.

## Step 1 — Establish the two sides

You need an old and a new artifact, not a diff. Reading the diff alone
cannot tell you a struct's size changed.

- PR or branch: the merge base is the old side.
- "Since the last release": the released artifact is the old side — a very
  different question. See
  [baselines and comparability](references/shared/baseline-and-comparability.md).

Build both sides under the **same** toolchain and flags, or the comparison
will be refused or dominated by toolchain noise
([compiler and build profiles](references/shared/compiler-and-build-profiles.md)).

The mechanics — worktrees, released artifacts, stored snapshots, and the
preflight checklist — are in
[getting the two sides](references/getting-the-two-sides.md).

## Step 2 — Choose the evidence depth

`--depth headers` is the floor for reviewing a source change: `binary` depth
cannot see a signature or layout change at all. Go deeper (`--depth build`,
`--depth source`, with `--sources`/`--build-info`) when flags, macros, or
reachability are in question. See
[evidence and depth](references/shared/evidence-and-depth.md).

## Step 3 — Run the comparison

```bash
abicheck compare OLD NEW \
  --depth headers \
  --scope-public-headers \
  --report-mode root-cause \
  --format json \
  -o compare.json
```

Add as the situation requires:

- `--header PUBLIC_HEADER` (repeatable) when the public headers are not
  auto-discoverable.
- `--policy plugin_abi` / `--policy sdk_vendor`, or `--policy-file`, when the
  project has its own view of what a given change kind means
  ([policies and suppressions](references/shared/policies-and-suppressions.md)).
- `--contract-evaluation --contract public` when you need per-finding
  contract relevance and its coverage ledger
  ([public surface and scoping](references/shared/public-surface-and-scoping.md)).
- `--suppress FILE` only when the project already has a suppression file.
  Never author one here.

## Step 4 — Read the report in order

Follow
[report interpretation](references/shared/report-interpretation.md)
exactly. The order matters:

1. `verdict: null` → **not comparable**. Read `reason`, remediate the
   inputs, re-run. Do not continue into the findings, and never report this
   as "no breaking changes found".
2. `evidence_tier`, `evidence_tiers`, `coverage_warnings`,
   `scope.resolved` → what the run could actually see.
3. `verdict` and `summary` → the compatibility answer.
4. `severity.*` → the grading of that answer, present whenever
   severity-aware grading was resolved from any source (a flag, the
   project's `.abicheck.yml`, a run profile, or a gate pack) — not only
   from a flag you passed.
5. `contract_coverage_failures` /
   `contract_coverage_exit_contribution` → the orthogonal coverage axis.
6. `root_causes` / `root_cause_count` → the findings, grouped.

## Step 5 — Group and attribute

Never summarize the flat `changes` array. Use abicheck's own
`root_causes` grouping and rank the groups; see
[root-cause grouping](references/shared/root-cause-grouping.md).

For each group, state the single underlying source change, its blast radius,
and whether it is the library's own change or toolchain/dependency churn.

### Branch: "why did this suddenly report dozens of breaks?"

This is the same workflow, entered from a different question. Work the
causes in this order, and stop at the first that explains the volume:

1. **Scoping.** Was `--scope-public-headers` used? Is `scope.resolved`
   true? An unscoped run reports internal and standard-library churn as
   findings.
2. **Toolchain drift.** Did the two sides use different compilers, standard
   libraries, or `-std=` values? A libstdc++ or dual-ABI change regenerates
   template instantiation symbols wholesale.
3. **Baseline.** Is the old side the intended baseline, or did it silently
   become an unrelated build?
4. **One real cause with a wide blast radius.** A single added struct member
   legitimately produces dozens of findings — `root_causes` shows this
   immediately.
5. **Genuinely many real breaks.** Report them.

Fixing scoping or the profile is the remediation for 1–3. Authoring a
suppression is not.

## Step 6 — Report

Deliver, in this shape:

- **Verdict**, in the user's own contract terms, with the exit code.
- **What could and could not be verified** — the evidence tier, anything
  unchecked, and any coverage failure. Never omitted.
- **Root causes**, ranked, each traced to specific findings.
- **Remediation per cause**, from
  [the remediation catalogue](references/shared/remediation-catalog.md)
  — for the cause, not per symptom.
- **What is out of scope of this answer** — e.g. packaging and behavioural
  compatibility, or the wider dependency graph (`abicheck deps compare`).
  A *raised symbol-version floor* is **not** in that list: `compare` emits
  `runtime_floor_raised` as a risk and can promote it to a break against
  declared floors, so read it from the findings rather than deferring it.

Optionally, once a verdict exists, offer to wire the same check into CI:
[CI wiring](references/shared/ci-wiring.md). Offer; do not do it
unasked.

## Termination criteria

The job is done when:

- a verdict exists from a real comparison (not a refused one), **or** the
  refusal is reported as its own outcome with its remediation;
- every claim traces to a finding and an evidence tier;
- anything unverified is stated as unverified;
- if a remediation was applied, the **same** comparison was re-run and the
  new result reported.

It is not done because a plausible explanation was produced. See
[safety invariants](references/shared/safety-invariants.md).
