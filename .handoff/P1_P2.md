# P1 / P2 analysis: unused and unrecorded policy rules, and the `id:` naming mismatch

Repository: `/home/user/abicheck`, HEAD `026a6109e` (v0.7.0). Analysis only; no repository files were modified. Reproduction scripts are in `/tmp/claude-0/-home-user-abicheck/2a2d264d-bafb-5ce8-a11f-61592ecad84a/scratchpad/analysis/` (`exp_p1p2.py`, `exp_a1.py`, `exp_rid.py`), run with `PYTHONDONTWRITEBYTECODE=1`.

## 0. Summary, and where the bug report is incomplete

- **P1 is confirmed** for reclassify and for suppression. Zero-match rules are absent from `disposition_audit.rules` and `disposition_audit.reclassifications` by construction, because both are projections over ledger *records*, and a rule with no records has no row.
- **P1 has two more cases the report does not name.** (a) A reclassify rule that matches but leaves the verdict unchanged is also absent. (b) A suppression rule that matches a finding already claimed by an earlier rule is absent (first-match credit). The second case is a direct breach of ADR-067's "overlapping rules with a stated winner" expectation.
- **Correction:** stale suppression rules are *not* only in `effective_config_fields`. The standard JSON report also carries a separate top-level `suppression_audit.stale_rules` block, attached unconditionally whenever a suppression file is in play. It is not reconciled with `disposition_audit`, has no counts in JSON, and counts overlapping matches, so a shadowed rule is reported as "not stale" while `disposition_audit` says it disposed of nothing.
- **P2 is confirmed.** `id:` is rejected as an unknown key (exit 64 through click's usage-error remap). `label:` is accepted and becomes `rule_id` for reclassify rows. The naming problem is wider than the report says: `rule_id` means three different things, the reclassify fallback collapses distinct rules into one row, and the two grammars spell the same concept differently (`kind` vs `change_kind`).
- **Docs overclaim.** `docs/use/ci-gating.md:180-181` says `suppression.strict: true` fails on unused/expired rules. Code path: `workflows/compare_configuration.py:471,507` -> `strict_suppressions` -> `frontends/cli/options/params.py:313-315` -> `SuppressionList.check_expired_strict()` (`policy/suppression/rules.py:942-953`). It checks expiry only. No unused-rule check exists anywhere in the gate path.
- **A test pins the bug.** `tests/test_disposition_reclassification.py::test_no_reclassify_rule_leaves_the_overlay_absent` (line 128) configures a real reclassify rule (`symbol: bar`, which does not match the finding `foo`) and asserts `reclassifications == ()`. Its name says "no rule", but a rule is configured.

## 3. Root cause, P1

The audit is a projection of the **records**, not of the **configured rules**. Three mechanisms compound.

1. **No rule inventory reaches the ledger.** `finalize_ledger` (`disposition_close.py:324`) and `ledger_for` (`:587`) build rows only from changes. `DiffResult` keeps the suppression file's digest and path (`checker_types.py:239`) but not the rule list, and reclassify rules are reachable only through `result.policy_file`. Nothing enumerates configured rules, so a rule with no records cannot appear. This is the core of the bug, and it is by construction, not a filter that drops rows.
2. **Every aggregator is record-derived.** `DispositionLedger.rules()` (`disposition_ledger.py:768-780`) skips rule-less records and tallies the rest. `reclassifications()` (`disposition_close.py:627-647`), `acknowledgments()` (`:662`) and `scope_reasons()` (`:704`) do the same. Zero rows are unrepresentable.
3. **Credit is given only where a rule was the decider.**
   - Suppression: `SuppressionList.evaluate` returns on the first match (`rules.py:776`). A shadowed rule never gets a record, so it is invisible (A2).
   - Reclassify: `reclassify_rule_for_change` returns `None` for a matching rule whose verdict is unchanged (`reclassify.py:755-756`), so a matched no-op is invisible (B2). Only a verdict-changing rule is stamped (`disposition_ledger.py:593`).

The existing stale-rule machinery does not fix this. `SuppressionList.audit()` (`rules.py:828-940`) counts every match (`:913`), so it disagrees with the disposition model on overlap, and it is suppression-only. Its JSON output carries labels only (`reporter_contract_blocks.py:340-`). The `--audit-suppressions` opt-in is gone (ADR-068 D4), but `attach_suppression_audit` is unconditional, so `stale_rules` is present in JSON whenever a suppression file is given.

The "why it is only in `effective_config_fields`" statement in the report is true for reclassify (`effective_config_digest.py:360-381` and the `policy.reclassify` key at `:501`, `:607`), and for suppression through the `suppressions` digest (`:566`). It is not the whole picture for suppression, because of `suppression_audit`. The `effective_config_fields` view also filters out expired rules (`active_reclassify_rules`), so expired rules disappear there silently.

## 4. Root cause, P2

- **`id` is rejected by design of the grammar, not by accident.** Neither `RECLASSIFY_KNOWN_KEYS` (`reclassify.py:176-193`) nor `_KNOWN_ENTRY_KEYS` (`rules.py:52-70`) defines a user-chosen identifier. The loader rejects unknown keys (`policy_file.py:383-388`, `rules.py:679-686`), `PolicyError`/`ValueError` becomes `click.BadParameter` (`params.py:308-311`, `:326-327`), and `_AbicheckGroup` remaps exit 2 to 64 (`runtime.py:233`).
- **There is no defined rule identifier.** ADR-067 D3 (`:298`) promises a "rule id" but does not define it. The implementation derived two different things:
  - Suppression: the canonical `rule_identity()` string (`rule_identity.py:55-80`), with `label` kept as its own field.
  - Reclassify: `label or reason or to_verdict.value` (`disposition_ledger.py:593`), which is prose or the target verdict. That collapses rules (B3) and drops the reason (B4).
- **Two precedences for one concept.** `rule_provenance` uses `identity or label or reason` (`rule_provenance.py:86`). The reclassify path uses `label or reason or verdict`. The same field name `rule_id` appears in `disposition_audit.rules[]` (identity) and `disposition_audit.reclassifications[]` (prose/verdict), so consumers cannot treat them alike.
- **Spelling asymmetry.** Suppression uses `change_kind`; reclassify uses `kind` (`reclassify.py:176-193` vs `rules.py:52-70`). `to:` exists only in reclassify, and `finding_id`, `reachability`, `allow_public_break`, `allow_unknown_reachability` exist only in suppression.
- **Duplicate entries are indistinguishable.** Two identical lines in one file produce the same identity, so `fold_disposition_audits` (`disposition_audit.py:272-400`) would merge them. A rule key needs `(source_file, entry index)` for uniqueness, with identity or `id` for display.

## 5. Proposed fix design

### 5.1 Configured-rule inventory (fixes P1 at the root)

- New leaf module, for example `abicheck/policy/rule_inventory.py`, that builds `ConfiguredRule` records from three sources: `result.policy_file.reclassify`, the suppression rule list (new `DiffResult` field next to `suppression_source_sha256`, set where the `SuppressionList` is in scope: `checker.compare` and `compare_finalize`), and acknowledgment records.
- Each `ConfiguredRule` carries a unique key `(kind, source_file, index)`, a display identity (`rule_identity` or the new `id`), `label`, `reason`, `expires`, and the selector set.
- `finalize_ledger` / `ledger_for` (`disposition_close.py:324`, `:587`) accept the inventory. `reclassifications()`, `acknowledgments()` and `DispositionLedger.rules()` are rewritten to iterate the inventory and join records to it, so one row exists per configured rule, including zero-count rows.
- Keep `DispositionLedger.rules()` (`disposition_ledger.py:768`) as the record tally, but have `compute_disposition_audit` (`report/disposition_audit.py:230-269`) merge it with the inventory.

### 5.2 Counting semantics (state explicitly, do not overload `matched_count`)

Four quantities, all per configured rule:

| Field | Meaning | Source |
|---|---|---|
| `matched_count` (existing) | findings the rule *disposed of*: first-match credit for suppression, verdict-changing decider for reclassify. Keep the meaning; the existing docstring at `disposition_audit.py:100` already says "disposed of". | ledger records |
| `shadowed_count` (new, additive) | findings the rule selector matched but an earlier rule claimed (suppression), or a matching no-op (reclassify) | `SuppressionOutcome` gains shadowed matches (`rules.py:755-787`); reclassify returns a richer result than `None` (`reclassify.py:755-756`) |
| `status` (new, additive) | `active` (disposed > 0), `unused` (detector ran, zero selector matches), `shadowed_only` (matched, disposed 0), `not_evaluated` (the rule's detector did not run; ADR-067 D3), `expired` (ADR-065/067 "stale" vs "expired" split, already tested at `test_suppression_audit_dates_and_boundaries.py:86-108`) | inventory + `not_evaluated_detectors` |

Hard rule: `unused` must never be reported when the rule's detector or comparison did not run. A Windows-only rule in a Linux run is `not_evaluated`, not `unused`. This follows ADR-065's "absent is not removed" and ADR-067 D3's `not_evaluated`.

For reclassify, `changed_count` is the existing `reclassifications[].matched_count` (verdict-changing). Add `matched_count` for selector hits so that a no-op rule reads as matched-but-unchanged.

### 5.3 Opt-in gate (P1 part two)

- Config: `unused_rules: allow | warn | block`, default `allow`, placed at the top level of the policy document (add to `KNOWN_POLICY_FILE_KEYS` in `policy/policy_file_top_level.py`). Vocabulary and precedence follow the acknowledgment gate (`acknowledgment_gate.py:70-151`, ADR-067 D6, `allow` default). Plus `--fail-on-unused-rules` (mapped to `block`).
- Semantics: `warn` lists rows with `status: unused` and does not change the exit code. `block` sets a `0`/`1` contribution, so a clean `0` becomes `1`, and `2`/`4` are never lowered (see 5.6).
- Do not overload `suppression.strict`. Today it means "expired" (`compare_configuration.py:471`, `params.py:313-315`). Changing it to also mean "unused" changes the exit code for existing users. That needs an ADR and a migration (AGENTS: "A direction stated in the vision is not permission to change an existing default, exit code"). The docs line at `ci-gating.md:180-181` should be corrected now, separately.
- Evaluate `block` over *configured* rules that are `status: unused` only. `not_evaluated`, `expired` and `shadowed_only` never trigger it.
- For release/aggregate runs, a rule may be unused in one matrix leg and used in another. Make the gate per-comparison by default and state that a shared policy file across a matrix will flag unused rules in legs that never exercise them. Alternatively, evaluate it at release level over the union (open question 3).

### 5.4 P2 naming

Recommended (non-breaking):
- Accept `id:` as an optional, user-chosen, file-unique identifier in both `RECLASSIFY_KNOWN_KEYS` and `_KNOWN_ENTRY_KEYS`. Duplicate `id` in one file is a `PolicyError`. The identifier becomes `rule_id` in the audit.
- When `id` is absent, `rule_id` is the canonical identity (`rule_identity`), for both grammars. Reclassify rows stop using `label or reason or verdict` as the key.
- `label` stays a grouping tag, `reason` stays prose; both are surfaced as their own fields in reclassify rows, as suppression rows already do (`rule_provenance.py:57-68`).

Compatibility trade-off: switching reclassify `rule_id` from label/reason to identity changes existing values in `reclassifications[].rule_id` and `reclassified_by` (`change_json.reclassified_by_for_change` mirrors the same precedence; `test_disposition_reclassification.py:170` pins agreement). Either (a) accept the change with a schema note and changelog, or (b) keep `reclassified_by` as is and add `rule_key`. Recommend (a) for `rule_id`, with the old value kept in `label`/`reason`, because the current value is not a stable identifier (B3).

Also consider unifying the spelling: accept `change_kind` as an alias of `kind` in reclassify (or the reverse), additive only.

### 5.6 Exit-code implications

- New axis: `unused_rules_contribution` in `ExitDecision` (`exit_decision.py:388`), `0`/`1` only, folded by `max` like `additions_review_contribution`. `exit_without_analysis_assurance()` (`:390-418`) already iterates every `*_contribution` field, so it picks the new field up automatically. Add an `ExitReason` enumerator and its entry in the reason map (`:582`).
- Never lowers an existing result: `max` cannot turn `2`, `4`, `7`, `16` or `8` into `1`.
- Legacy scheme: `1` is a new reason for an otherwise clean run, equivalent to contract coverage. Severity-aware scheme: `1` is documented as "error-level in `addition`/`quality_issues` only" (`exit-codes.md` ~`:470-476`). An unused rule is a quality issue, so folding it to `1` fits, but this must be stated explicitly; see open question 2.
- Documentation: add a row to the fold table at `docs/reference/exit-codes.md` ~`:200-208` and the severity table.
- Default `allow` keeps every existing exit code unchanged. This is the condition for shipping without an ADR amendment to the exit contract.
- Release fan-out: `release_exit_decision.py:92` (`release_additions_review_contribution`) is the precedent to copy. `outcome_release.py:104` must list the new contribution.

### 5.7 Schema implications

- `disposition_audit` (compare report, schema changelog `schemas/__init__.py:725-727`): additive `shadowed_count`, `status`, and an unused-rules total on each row. Add a `#:` entry as the next number in that series (2.54 at the time of writing; check the series head before numbering, per the "renumber, don't reuse" convention). Existing `matched_count` keeps its meaning.
- Zero rows appear in existing arrays (`rules`, `reclassifications`, `acknowledgments`). That is a semantic change for consumers that assume non-empty rows. Note it in the changelog.
- `suppression_audit.stale_rules` (`schemas/__init__.py:307`, `release_schema.py:222`): derive from the same inventory. Keep the block for compatibility; document that it is now a projection of the disposition inventory.
- `effective_config_fields` (`effective_config_digest.py`, keys at `:113`, `:501`, `:607`): if `policy.unused_rules` is added as a key, every run's digest changes unless the key is emitted only when non-default. Check `tests/test_effective_config_digest.py` before choosing.
- `REPORT_SCHEMA_VERSION` is `6.2` (`schemas/__init__.py:1095`). The `#:` changelog series (2.x) and the top-level version are separate numbering; the implementer must decide which bumps.
- Release schema (`release_schema.py`): mirror the exit contribution and the audit fields.

### 5.8 ADR-067 compliance

- "Record before disposing" is satisfied: configured rules are enumerated before disposition, and every disposition keeps its rule (`rule_id`, reason, source file). "100 removals suppressed by rule X" stays visible.
- "Overlapping rules with a stated winner" (ADR-067 acceptance list, ~`:414-423`) is satisfied by `shadowed_count` plus the winner's identity. Currently it is not.
- The `unused` gate is a *policy* decision (ADR-067 D6 vocabulary) and does not change observed facts, which matches "Policy decides acceptance, not facts" in `AGENTS.md`.
- "Absent is not removed" (ADR-065) is the reason `not_evaluated` must be a separate status.

### 6.2 Generalized invariant tests (new module, for example `tests/test_disposition_rule_inventory.py`)

Register the bug class under the existing `policy.disposition_conservation` family in `tests/regressions/manifest.py` (AGENTS: "a bug fix's regression test targets the bug class"). Use `pytest.mark.parametrize` for the fast lane and a Hypothesis test marked `slow` (per `tests/CLAUDE.md`).

Generator: snapshot shapes from `_snapshots` (existing helper); rule sets drawn from `{symbol exact, symbol_pattern re, change_kind, reason, label, expires in past/future}`, lists of length 0-4, including duplicates, zero-match, overlapping, and combinations of all three rule types (suppression, reclassify, acknowledgment). Oracle: a small, separate evaluator written in the test using `re.fullmatch` and string equality over the generated subset. It must not call `Suppression.matches`, `ReclassifyRule.matches`, or `SuppressionList.audit`.

Invariants:

- **I1 (inventory completeness).** The set of audit row keys equals the set of configured rule keys (non-expired), with multiplicity. Two rules with identical `label` and `reason` yield two rows. Duplicate lines in one file yield two rows.
- **I2 (suppression counting).** For each suppression rule R: `matched_count(R)` == number of detected findings for which R is the first configured rule (oracle order = file order) that matches. `shadowed_count(R)` == findings R matches minus `matched_count(R)`. The sum of `matched_count` over suppression rows == `len(suppressed records)`.
- **I3 (zero match).** A configured rule with no matching findings has a row with `matched_count == 0`, and `status == "unused"` when its detector ran, `"not_evaluated"` when it did not (use a snapshot pair with DWARF absent for a DWARF-only rule), and `"expired"` when past `expires`.
- **I4 (reclassify matched vs changed).** For each reclassify rule R: `matched_count(R)` counts selector hits including no-op matches; `changed_count(R)` counts verdict-changing decisions. `sum(changed) == reclassified_total`.
- **I5 (observational inertness).** Adding a configured rule that matches nothing changes exactly one audit row, and no count, verdict, effective total or exit code. Removing it removes exactly that row. (Metamorphic; compare two full `compare()` results.)
- **I6 (fold).** `fold_disposition_audits` over N members: each inventory key appears once, zero rows survive, `matched` and `shadowed` sum across members, and duplicates across members stay distinct.
- **I7 (gate).** With `unused_rules: block`, `exit.code == max(prior, 1)` iff at least one row has `status == "unused"`. Never lowers `2`/`4`/`7`/`8`/`16`. With `warn`, exit code unchanged and the row is listed. With `allow`, unchanged.

Sketch (fast, parametrized, not the implementation's own helper as oracle):

```python
@pytest.mark.parametrize("shape", SHAPES)
@pytest.mark.parametrize("rule_set", RULE_SETS)   # includes [], zero-match, overlap, dup, mixed types
def test_every_configured_rule_has_exactly_one_audit_row(shape, rule_set):
    old, new = _snapshots(**shape)
    result = compare(old, new, suppression=..., policy_file=...)  # built from rule_set
    rows = audit_rows(compute_disposition_audit(result))           # keyed by inventory key
    assert sorted(rows) == sorted(configured_keys(rule_set))       # I1
    for key, rule in configured(rule_set):
        assert rows[key].matched == oracle_disposed(rule, rule_set, result)   # I2/I4
        assert rows[key].status == oracle_status(rule, result)                 # I3
```

### 6.3 P2 invariant tests

- **P2-RT (round trip).** For every key `k` in `RECLASSIFY_KNOWN_KEYS` and `_KNOWN_ENTRY_KEYS`, assert `k` is classified in one table: identity (`id`, `label`), selector, prose (`reason`), gate, expiry, target (`to`). Then, for every identity-classified key, a rule that sets it round-trips to the audit row (`id` -> `rule_id`; `label` -> `label`). A key that is accepted but not classified, or classified but not surfaced, fails the test. This is the property the bug report asks for.
- **P2-CLI.** A `CliRunner` case: a policy with `id:` exits `64` (today; after the fix, it exits `0` with the row present, or stays `64` with a documented reason). The test pins whichever decision is made.
- **P2-collide.** Two reclassify rules with identical `reason` and different selectors yield two rows, with `rule_id` distinct. Duplicate `id` in one file raises `PolicyError`.
- **P2-name parity.** Both grammars accept `kind`/`change_kind` (or the chosen single spelling), with a table test.
